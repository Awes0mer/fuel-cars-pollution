# Fuel, Cars & Pollution: a HydraDB graph that refits its own links every year

HydraDB Hackathon, Track 1 ("a graph that improves itself, sharper every run").

Crude oil → gasoline → fuel use → U.S. transport CO2, with miles driven and electric-car adoption feeding in. Each link's strength is stored in a self-hosted HydraDB graph and refit every year, so each correction changes the next prediction. It is tested walk-forward, on years not used to design it, against a vector-store-style k-nearest-neighbour lookup and a "no change" guess.

- Live app: https://awes0mer.github.io/fuel-cars-pollution/ (GitHub Pages, published from the `gh-pages` branch, which holds the `site/` folder).
- Walkthrough video: not recorded yet.

## What it is

A nowcast: when a year closes, the graph estimates how much U.S. transport CO2 changed, before the official figure is final. It knows that year's crude oil price, gasoline price, vehicle-miles and the electric share of new car sales. It does not know fuel use or CO2 yet.

1. **Predict.** Query HydraDB for the links pointing into `FuelUse`, read their weights, predict fuel use; then read the links into `CO2` and push the predicted fuel use one more hop.
2. **Correct.** When the real figures arrive, refit each target's weights by recursive least squares with forgetting, and write them back to HydraDB with a per-year history node.
3. **Repeat** next year with the corrected weights.

The site also shows the data behind it (fuel prices, miles driven, vehicles per 1,000 people, EV share, transport CO2 and highway-vehicle pollutants) and correlations of year-over-year changes.

## How HydraDB is used

- Engine: `hydra-db/hydradb` v0.4.0 `graph-node`, self-hosted, local mode (`CLOUD_PROVIDER=local`), started by `scripts/run_hydradb.sh` with a new empty store, a new random token, `GRAPH_USAGE_REPORT_ENABLED=false`, and all listeners bound to 127.0.0.1. The engine is not in this repository.
- Graph: `Variable` nodes (Crude, Gasoline, VMT, EVShare, FuelUse, CO2); `Link` nodes holding the learned weight; `Fit` nodes holding each target's intercept and RLS covariance; `LinkState` history nodes (one per link per year); `Prediction` nodes. Edges: `FEEDS`, `INTO`, `FITS`, `HISTORY`, `OF`.
- Links are nodes because v0.4.0 deduplicates edges on (source, target, type): an edge cannot carry a weight that changes and keeps history.
- Each prediction is a graph walk: `MATCH (t {id: $id})<-[:INTO]-(s) RETURN s.id`, then anchored id reads of each link and fit node.
- Writes use the documented shapes: `UNWIND $rows AS row MERGE (n {id: row.id}) SET n:Label, n.p = row.p` for nodes (labels cannot sit in an UNWIND pattern), `UNWIND … CREATE` for edges, `MATCH (n {id: $id}) SET …` for updates.
- This run: 2167 HTTP queries in 34.61 s; graph after the run: 6 Variable, 5 Link, 3 Fit, 240 LinkState, 138 Prediction.
- Same code on an in-memory store gives the parity check.

Engine notes found while building (v0.4.0):

- `graph-node` binds to 0.0.0.0 by default; `GRAPH_HTTP_ADDR`, `GRAPH_BOLT_ADDR` and `GRAPH_ADMIN_ADDR` set it to loopback.
- Floats do not always round-trip exactly: 34 of 300 test values came back one ULP off (`results/hydradb_float_roundtrip.json`). That is a likely cause of the 1.25e-10 pp gap between the HydraDB and in-memory predictions (not proven). Storing exact bit patterns (for example hex strings) would rule it out.
- `count(n)` is rejected; `count(*)` and `count(n.prop)` work.
- Node ids must be non-negative integers.

## Pre-registered rule

Full text: [PREREGISTRATION.md](PREREGISTRATION.md). It was committed before the first run and not edited afterwards. PASS needs all four:

1. HydraDB and in-memory predictions agree within 1e-9 pp.
2. Graph holdout MAE ≤ 0.90 × no-change MAE.
3. Graph holdout MAE ≤ 0.90 × k-NN MAE.
4. Graph holdout MAE < frozen-graph MAE (refitting must help).

Run history, for honesty:

1. Runs 1 and 2 crashed in the HydraDB step (a batching bug in this project's store code, then `count(n)` being unsupported) before any holdout score was computed or printed.
2. Run 3 completed (archived in `results/archive/run3_learning_results.json`). An independent code review then found that its k-NN baseline only used neighbour years that also had every other input, which PREREGISTRATION.md does not ask for. Run 3 tuned k-NN to k = 5, window 10, and scored it 2.92 on the holdout.
3. Run 4 implements the pre-registered k-NN wording exactly and re-tunes it on the design years only: k = 7, window 10, holdout 2.95. The graph, the rule, the periods and the metric did not change. Run 4 also reports the HydraDB run's own predictions.
4. Run 5, the result above, fixes a storage bug a CodeRabbit review found: link-history and prediction node ids overlapped for two links, so HydraDB merged those node pairs. Predictions never read those nodes; every prediction and link weight is identical to run 4 (largest prediction difference 0). Run 4 is archived next to run 3.

## Limitations

- Small sample: 18 holdout years; the intervals above are wide.
- The author knew the broad history of the holdout years (2008, 2020) even though settings were picked on 1982–2004 only.
- Inputs are revised (final) values from today's files, not real-time vintages; real-time accuracy is unmeasured.
- Nowcasting is narrow: EIA publishes the real CO2 figure within months. The value shown is the learning loop, not a forecast product.
- U.S. only for the learning loop. World series are shown but not modelled.
- The "what the links imply" calculator on the site is arithmetic on the final weights; it was not tested as a scenario model.
- The k-NN baseline is one reasonable plain-store design (same inputs, standardised, RMS distance over shared dimensions). Other designs could score differently.

## Reproduce

```bash
python -m pip install -r requirements.txt
python -m fcp.fetch        # download files, write data/manifest.json
python -m fcp.parse        # data/processed/series.json
bash scripts/run_hydradb.sh <path-to-graph-node> .hydradb/token   # inside WSL/Linux, separate shell
python -m fcp.experiment   # pre-registered run -> results/learning_results.json
python -m fcp.roundtrip    # float round-trip check
python -m fcp.stats        # correlations and summary
python -m fcp.site         # static site in site/
python -m fcp.ogimage      # share image site/og.png
python -m fcp.readme       # this file

```
